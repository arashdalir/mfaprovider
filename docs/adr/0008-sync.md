# ADR-0008: Sync via user-selected cloud file (post-MVP)

- Status: accepted (2026-11-12)
- Date: 2026-11-12
- Related tasks: TASK-0001

## Context
User wants to point the app at a Google Drive / OneDrive / other cloud file. The vault is already end-to-end encrypted, so a provider only sees ciphertext.

## Options considered
1. **Provider-agnostic file/folder** — user picks a path; Google Drive/OneDrive/Dropbox desktop clients and Syncthing do the transport. On Android, the Storage Access Framework exposes cloud document providers. No OAuth, no tokens in our app.
2. WebDAV — covers Nextcloud and many hosts; needs credentials storage.
3. Direct Google Drive / OneDrive APIs — best UX, but OAuth app registration/verification, token storage, and a network permission surface.

## Decision
Phased behind a `StorageProvider` trait in `mfa-sync`: phase 1 file/folder (+ Android SAF), phase 2 WebDAV, phase 3 direct Drive/OneDrive.
- Sync unit = the encrypted vault file; same password on all devices. Biometric key wraps are device-local and never synced.
- Merge per entry by `id`, last-writer-wins on `updated_at`, tombstones for deletes (ADR-0004); merge is done on decrypted data inside the core, then re-encrypted.
- Conflict copies created by cloud clients ("... (conflicted copy)") are detected and merged, not ignored.
- Atomic writes (temp file + rename) and a header version/etag to avoid clobbering concurrent changes.
- Sync is opt-in; until enabled the app holds no network permission-related code paths.

## Consequences
+ Works with any cloud immediately; no secrets for cloud accounts held by us in phase 1.
- Clock skew affects LWW (mitigate with hybrid logical clocks later if needed).
- Delayed cloud-client propagation means eventual, not instant, consistency.
